# Gather / 構造化対話

ユーザーの漠然としたアイデアや目標を、対話を通じて明確な形に構造化する。

**The reversal**: ユーザーが rough idea を持ってくる → AI が的確な質問で真のニーズを引き出す → 二人で明確な成果物に収束させる。

## Clarity Assessment（最初のステップ）

対話開始前に、ユーザーの intent がどの程度明確か評価する。核心3軸（Who/What/Why）のうち何軸が言及されているかで判定：

- **>=90% 明確**（Who/What/Whyの3軸が全て言及済み）→ 質問をスキップ。即座にドラフト仕様を出力。「具体的ですね。ドラフト仕様を書きます。修正しますか？」
- **60-90% 明確**（1-2軸が未言及）→ 的を絞った質問を1-2問のみ
- **<60% 明確**（Whatすら曖昧、または一文のみの発話）→ オープニング質問から開始し、反復

## セッションフロー

### Turn 1: オープニング

1つの質問で始める：
> 何を作りたいですか？（または: 何を達成したいですか？何について考えたいですか？）

### Turn 2+: 段階的精製

**1ターンにつき1問**。最も不明確な軸を狙う：

**アイデアが大きすぎる場合**: 1つのセッションで全要件を詰めようとせず、スコープを分割する。ユーザーのアイデアが複数の独立した機能・領域にまたがる場合、最も重要な1領域にフォーカスを絞り、他は Out of Scope に回す。「このアイデアは複数の領域にまたがっています。まず [領域A] に絞って要件を固めましょう。残りは別セッションで扱いましょうか？」

### モード判定と軸

ユーザーの最初の発話から自動的にモードを判定する。以降の質問の軸と最終フォーマットが変わる。

**buildモード**（ソフトウェア・プロダクト要件）— 「作りたい」「開発したい」「システム」「ツール」「アプリ」等:

| 軸 | 観点 |
|---|---|
| Who | ユーザー？対象者？ステークホルダー？ |
| What | 機能？スコープ境界？成果物？ |
| Why | 解決する課題？根本的なゴール？ |
| How | アーキテクチャ？技術スタック？連携先？ |
| Constraints | タイムライン？パフォーマンス？既存システム？ |
| Quality | 信頼性？テスト？保守性？ |

**directionモード**（個人目標・キャリア・非技術的な構想）— 「なりたい」「やりたい」「目指したい」「方向を決めたい」「整理したい」等:

| 軸 | 観点 |
|---|---|
| What | 何を達成したい？どんな状態を目指す？ |
| Why | なぜそれが重要？根本的な動機は？ |
| Current | 今の状況は？何が足りない？ |
| Gap | 目標と現状の間に何がある？ |
| Constraints | 時間？リソース？環境的制約？ |
| Success | どうなったら「できた」と言える？ |

### 出力フォーマット（Turn 2以降の毎ターン）

**A. 現時点の仕様**
これまでに判明した情報に基づく最良の仕様ドラフト。常に含める。初期ターンでも完成度を高く。毎ターン洗練させ、最終ターンではそのまま仕様書として使える状態に近づける。

**B. 提案**
ユーザーが気づいていない改善点や考慮事項を2-3個。

**C. 質問**
1つの的を絞った質問。要件が十分明確なら、次の質問ではなく確定を提案。

### 選択肢の提示（原則：常に提示）

**デフォルトは選択肢あり。** Cセクションの質問には、原則として2-4個の選択肢を番号付きで付ける。
ユーザーは番号で選ぶか、自分の言葉で回答できる。

```
**[トピック] の選択肢:**
  1. [具体的な選択肢] — [理由]
  2. [具体的な選択肢] — [理由] (recommended)
  3. [具体的な選択肢] — [理由]
```

選択肢なしの自由回答にしてよいのは、以下のような純粋に探索的な質問のみ：
- アイデアの全体像を引き出す最初の1問
- ユーザーの独自の考え方や好みを引き出したい場合

「誰が使う？」「経験レベルは？」「どの技術を使う？」「環境は？」等の
カテゴリ・レベル・選択で回答できる質問では、**必ず** 選択肢を提示すること。

## 確定フェーズ

ユーザーが満足するか、内容が確固たるものになったら：

1. **最終仕様 / 最終整理** を構造化ドラフトとして出力
2. buildモードではなぜ実装可能か、directionモードではなぜ実行可能かを1文で添える
3. 「この内容で確定しますか？」と確認

ユーザーがさらに洗練させたい場合は続ける。無理に閉じない。

確定トリガー:
- **ユーザー主導**: "done" / "finalize" / "これでいい" / "確定" / "完成" と言った場合
- **AI主導**: 6軸のうち4軸以上が確定した場合、確定フォーマットでドラフトを出し「この内容で確定しますか？」と確認する

## 出力フォーマット（確定時）

モードに応じてフォーマットを切り替える。

### buildモード: 要件仕様書

```markdown
# <要件タイトル>

## Goal
<何を、誰のために、なぜ実現するか。2-5文。>

## Users
- <主な利用者>
- <関係者・影響を受ける人>

## Scope

### In Scope
- <項目>

### Out of Scope
- <項目>

## Requirements
- <ユーザーができること / 必要な振る舞い>
- <必要なデータや状態>

## Decisions
- **<決定事項>**: <選択した方針> — <理由>

## Constraints
- <制約>

## Acceptance Criteria
- [ ] <基準>
- [ ] <基準>

## Assumptions
- <未確認だが仮置きしている前提>

## Open Questions
- <未解決の項目> — <解決しないと困る理由>
```

**Open Questions の扱い**: 全ての Open Questions を解決してから確定する必要はない。影響が小さい項目や後続フェーズで判断可能な項目は、Open Questions として残したまま確定してよい。ただし What や Scope に直結する未解決項目は、確定前に解決すること。

### directionモード: 方向性整理シート

```markdown
# <目標タイトル>

## Goal
<何を達成したいか、なぜか。2-5文。>

## Current State
<今の状況。あるがまま。>

## Gap
<目標と現状の差。埋めるべきもの。>

## Actions
- [ ] <具体的なアクション>
- [ ] <具体的なアクション>

## Constraints
<制約：時間、リソース、環境など>

## Success Criteria
- [ ] <どうなったら「できた」と言えるか>
- [ ] <基準>

## Open Questions
- <未解決の項目>
```

**Open Questions の扱い**: buildモードと同じ。

重要: ユーザーの言葉をそのまま使う。AIの解釈で言い換えない。
目標はユーザー自身のものなので、表現に寄り添うこと。

## 言語

- ユーザーの言語に合わせる（日英ミックス可）
- 技術用語は原語のまま
- 簡潔に。経験豊富な同僚とホワイトボードで議論する密度を狙う。

  2. リスト形式 — シンプル、実装コスト最小
  3. ガントチャート — スケジュール管理に強い
  4. テーブル形式 — 一覧性が高い、フィルタに強い

**Turn 3** (A/B/C):

  2. チーム内のタスク共有・進捗確認 — 担当者アサインや通知が必要
  3. プロジェクト全体の進行管理 — マイルストーン・期限管理が中心

主な利用シーンはどれに近いですか？

**User**: チーム内の共有かな。あとは特になくて、とりあえずシンプルに

# 開発チーム向けタスク管理ツール

## Goal
開発チーム5名が、スプレッドシートより少ない手間でタスクを共有し、進捗を確認できるようにする。Slackでのコミュニケーションと接続し、日常のタスク更新や通知の摩擦を減らす。

## Users
- 開発チームのメンバー5名
- タスク進捗を確認するチーム内の関係者

## Scope

### In Scope
- カンバン形式でのタスク一覧表示
- タスクの作成・移動・ステータス変更
- Slack通知
- Webとモバイルでの閲覧・操作
- カンバン列のカスタマイズ

### Out of Scope
- ガントチャート
- 大規模プロジェクト管理機能
- 高度なレポート・分析

## Requirements
- ユーザーはタスクを作成し、カンバン上で状態を変更できる
- ユーザーはスマホからタスク状況を確認できる
- タスク更新はSlackに通知できる
- カンバン列はチームの運用に合わせて変更できる

## Decisions
- **UI形式**: カンバン形式 — 5人規模のチームで直感的に進捗を共有しやすい
- **利用シーン**: チーム内のタスク共有・進捗確認 — 担当者アサインや通知が有効
- **初期スコープ**: シンプルなMVP — 作成・移動・ステータス変更・Slack通知に絞る

## Constraints
- 既存のコミュニケーション基盤はSlack
- モバイルからも使えること

## Acceptance Criteria
- [ ] 開発チーム5名がタスクを作成・移動・完了できる
- [ ] タスク更新がSlackに通知される
- [ ] スマホ画面でタスク一覧と詳細を確認できる
- [ ] カンバン列をチームの運用に合わせて変更できる

## Assumptions
- MVPでは複雑な権限管理や高度な分析は扱わない
- 既存のスプレッドシートからの移行は手動でも許容される

## Open Questions
- 認証方式 — チーム外からのアクセスをどこまで制限するかを決める必要がある
- 担当者・期限・フィルタ機能 — MVPに含めるか、次フェーズに回すかを決める必要がある

5人規模のチーム向けで、初期スコープが作成・移動・ステータス変更・Slack通知に絞られているため、段階的に実装できます。

# フリーランス独立に向けた方向性

## Goal
会社員Webエンジニアとしての経験を活かし、1年程度かけてフリーランス独立を目指す。まずは副業で案件獲得の流れを作り、受託・請負または技術顧問の方向性を具体化する。

## Current State
現在は会社員Webエンジニア5年目。独立したい気持ちはあるが、具体的な行動はまだ始めていない。

## Gap
副業案件の獲得ルート、自分の強みの言語化、受託・請負と技術顧問のどちらを主軸にするかが未確定。

## Actions
- [ ] 自分の強みを3つ言語化する
- [ ] 副業案件の獲得ルートを調べる
- [ ] 知人紹介やコミュニティ経由で小さな案件候補を探す

## Constraints
会社員として働きながら、1年程度で準備する。自社サービス開発はリスクが高いため除外する。

## Success Criteria
- [ ] 副業案件を始める準備ができている
- [ ] 受託・請負または技術顧問の方向性を説明できる
- [ ] 独立までの大まかな準備ステップが見えている

## Open Questions
- 受託・請負と技術顧問のどちらを主軸にするか
- 副業案件をどの経路で獲得するか

1年程度の準備期間があり、まず副業から始める方針なので、会社員のまま段階的に実行できます。
