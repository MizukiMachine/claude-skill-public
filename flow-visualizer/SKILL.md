## 詳細フロー図形式とは

ASCIIアートを使ったフロー図で、以下の要素を組み合わせた説明スタイル：
1. **フロー図** - 処理の流れを縦方向のボックスで表現
2. **プログラミングレイヤー** - ファイル名、関数名、コマンド、終了コードなど
3. **自然言語の説明** - 「何をしているか」「なぜ必要か」
4. **適度な抽象度** - コード1行1行ではなく、処理の単位で
5. **入れ子構造** - メインフローの中にサブフローを表示

## 出力フォーマット
```
  入力（ユーザーコマンドやトリガー）
        ↓
  ┌──────────────────────────────────────────────────────────────┐
  │  Step 1: [処理名]                                          │
  │  [何をするか + プログラミングレイヤーの情報]                  │
  ├──────────────────────────────────────────────────────────────┤
  │  Step 2: [処理名]                                          │
  │  ┌─────────────────────────────────────────┐                │
  │  │ サブ処理のフロー（入れ子構造）            │                │
  │  │ - [詳細な処理内容]                       │                │
  │  │ - [プログラミングレイヤー]               │                │
  │  └─────────────────────────────────────────┘                │
  ├──────────────────────────────────────────────────────────────┤
  │  Step 3: [処理名]                                          │
  │  [結果や出力]                                               │
  └──────────────────────────────────────────────────────────────┘
        ↓
  最終出力
```

## 説明の原則

### 1. プログラミングレイヤーを含める
ブラックボックスにしすぎず、中でどう動いているかも見せる：
- ファイルパス（例: `internal/cli/root.go`）
- 関数名（例: `initConfig()`）
- コマンド（例: `go test ./...`）
- 終了コード（例: 0=成功、1=失敗）
- 環境変数（例: `GITHUB_TOKEN`）

### 2. 適度な抽象度を保つ
- コード1行1行まで掘り下げすぎない
- 処理の「単位」で説明する
- 技術的すぎず、初心者でも理解できるように

### 3. 自然言語で「何をしているか」を説明
プログラミング用語だけにならず：
- 「なぜこの処理が必要か」
- 「何が達成されるか」
- 「ユーザーから見てどう見えるか」

### 4. 入れ子構造で複雑さを表現
メインフローの中にサブフローを表示：
```
┌─────────────────────────────────────┐
│ メイン処理                          │
│ ┌─────────────────────────────────┐ │
│ │ サブ処理1                       │ │
│ │ ┌─────────────────────────────┐ │ │
│ │ │ さらに詳細な処理            │ │ │
│ │ └─────────────────────────────┘ │ │
│ └─────────────────────────────────┘ │
└─────────────────────────────────────┘
```

### 5. 短く簡潔に
各ステップは1-2行で説明。冗長な説明より、視覚的な構造で理解させる。

## 良い例と悪い例

### 良い例 ✅
```
$ go test ./...
      ↓
┌──────────────────────────────────────────────────────────────┐
│  1. *_test.go ファイルを検索                                 │
│  2. TestXxx 関数を検索                                       │
│  3. 一時的な main 関数を自動生成                             │
│  4. コンパイル                                               │
│  5. 実行                                                     │
│     ┌─────────────────────────────────────┐                 │
│     │ TestA() → PASS                      │                 │
│     │ TestB() → FAIL (エラーメッセージ)   │                 │
│     └─────────────────────────────────────┘                 │
│  6. 結果を集計して表示                                       │
│  7. 一時ファイルを削除                                       │
└──────────────────────────────────────────────────────────────┘
      ↓
  結果表示
```

### 悪い例 ❌（抽象度が高すぎる）
```
go test はテストを実行します。
1. テストを探す
2. テストを実行する
3. 結果を表示する
```
→ プログラミングレイヤーがなく、何が起きているか見えない

### 悪い例 ❌（詳細すぎる）
```
func TestMain(m *testing.M) {
    wd, err := os.Getwd()  // カレントディレクトリを取得
    if err != nil {         // エラーチェック
        fmt.Fprintf(...)     // エラーメッセージを出力
        ...
    }
    ...
}
```
→ コード1行1行まで書かれていて、全体像が見えない
