# Q&A Step Workflow

1問ずつQ&Aで対話しながら要件定義・設計・意思決定・理解を進める。

**重要: 全ての質問は AskUserQuestion ツールを使用して提示する。質問文はツールの `question` フィールドにのみ書き、テキスト側に同じ質問を重複させない。テキストは文脈・フィードバックの提示に限定する。ユーザーは選択肢をクリックするだけで回答できる。**

このスキルには2つのモードがある。ユーザーの入力に応じて適切なモードを選択する。

## モード判定

Phase 1（意思確認）の回答内容で判定する：

- **Decision モード**: 決定すべき事項がある（設計、技術選定、仕様決定等）
- **Understanding モード**: 対象を理解したい（概念の理解、コードの解説、仕組みの学習等）

両方が混在する場合は Decision モードを優先し、理解が必要な箇所で Understanding モードに切り替える。

## 全体フロー

```
[入力] → [Phase 0: コンテキスト収集] → [Phase 1: 意思確認]
       → [Phase 2: 決定グラフ生成] → [Phase 3: 対話ループ] → [Phase 4: 最終出力]
                                                         ↑        │
                                                         └── back ┘
```

## Phase 0: コンテキスト収集（非対話）

ユーザーに質問する前に、以下を自動収集する：

- プロジェクト/対象の現状構造
- 既に決まっていること（技術スタック、規約、制約）
- 関連する既存データ（SPEC.md、CLAUDE.md、既存コード等）

収集結果は内部保持し、Phase 2の材料にする。

## Phase 1: 意思確認（1問）

AskUserQuestionツールを使って、ユーザーの目的を確認する質問を1つ投げる。
選択肢には目的の方向性を2〜4個提示し、ユーザーが最も近いものを選ぶ。

この回答がモード判定と以降の全質問の起点になる。

## Phase 2: 決定グラフ生成（非対話）

Phase 0のコンテキスト + Phase 1の回答から、決定すべき変数リストを生成する。

### 変数の構造

| フィールド | 内容 |
|---|---|
| id | 一意識別子 |
| question | ユーザーに提示する質問文 |
| candidates | 選択肢（2〜4個）+ 各々の説明 + recommendedフラグ |
| depends_on | 依存する他の変数のIDリスト |
| classification | Ask（ユーザーに聞く）または Auto（自動決定） |
| auto_reason | Autoの場合、自動決定の理由 |

### Ask と Auto の分類ルール

**Askにする条件（いずれか）：**
- 複数の正当な選択肢があり、ユーザーの意図に依存する
- 方向性に大きな影響を与える決定
- ユーザーが明確な好みを持つ可能性が高い
- 後からの変更コストが高い

**Autoにする条件（全て）：**
- 既に決まっている（慣例・規約がある）
- 技術的に自明な選択肢が一つに絞られる
- ユーザーが変更する可能性が低い

### 候補生成ルール（推奨順、2〜4個）

1. 既存の慣例/使用実績があるもの（一貫性維持）
2. 既に導入済みのもの（追加コストゼロ）
3. エコシステムの主流な選択肢
4. 異なるパラダイムの代替を1つ
5. 文脈に合わせた具体性（汎用すぎる選択肢は避ける）

### 依存ツリー（DAG）

```
[根（大決定）] ← depends_on: [] → 最初に聞かれる
  ├─ [中決定A] ← depends_on: [根]
  │    └─ [葉決定X] ← depends_on: [中決定A]
  └─ [中決定B] ← depends_on: [根]
```

上流の回答が変わると下流の候補も変わりうる。だから1問ずつ順番に聞く。

## Phase 3: 対話ループ（1問ずつ）

依存ツリーの根から順に、1問ずつ進める。

### 各ターンの構成

AskUserQuestionツールを使って質問を提示する：
1. `question` フィールドに質問文
2. `options` フィールドに候補を推奨順に2〜4個。recommended候補は**先頭**に置き、label末尾に `(Recommended)` を付ける
3. `multiSelect` は false（単一選択）
4. 自由テキスト入力用の選択肢は作らない（「Other」はツールが自動で付ける）

### ユーザーの入力パターン

AskUserQuestionの選択肢に加え、ユーザーがテキストで入力する場合の動作：

| 入力 | 動作 |
|---|---|
| 選択肢クリック | 該当候補を選択 |
| `auto` / `任せる` | recommended候補を自動選択 |
| `back` / `戻る` | 直前の質問に戻る。下流の回答も連鎖的に無効化 |
| `summary` / `一覧` | 現在の決定状況（決定済み・残り・自動決定予定）を表示 |

### 次の質問の選び方

未回答のAsk変数のうち、全ての depends_on が満たされている最初のものを提示する。

### 途中サマリー

5問に1回、または重大な決定の直後に、現在の状態を一覧表示する。

### 終了条件

| 条件 | 動作 |
|---|---|
| 全Ask変数が回答済み | 自動的にPhase 4へ |
| ユーザーが「完了」 | 未回答が残っていれば一覧表示し、「未回答を置いて進むか？」確認 |
| 残りが全てAuto | ループを自動完了しPhase 4へ |

## Phase 4: 最終出力

### Decision モードの場合

全決定（ユーザー回答 + 自動決定）をまとめて成果物を生成する。

1. 全決定を一覧化したドキュメント
2. ユーザーによる最終確認
3. 保存先の選択（ファイル保存等）

### Understanding モードの場合

理解の到達点をまとめる。

1. 対話を通じて確認できた理解ポイントを一覧化
2. ユーザーが「まだ分からない」と言った箇所は未解決として明記
3. 次にどこから掘り下げるべきかの提案

---

## Understanding モードの詳細

Decision モードのPhase 2-3と同じ1問ずつの原則を踏襲しつつ、以下の違いがある。

### Phase 2 の違い（Understanding モード）

決定グラフの代わりに「理解すべき概念の依存リスト」を生成し、各概念を**マイクロステップ**（最大2文で言える知識単位）に分解する。

各概念は以下の構造を持つ：

| フィールド | 内容 |
|---|---|
| id | 一意識別子 |
| concept | 理解すべき概念名 |
| micro_steps | 最大2文の説明単位のリスト（1概念につき2〜5個） |
| depends_on | 前提となる概念のIDリスト |

生成ルール：
- 前提知識から順に並ぶ（依存の根から葉へ）
- 各概念は前の概念を理解していなければ理解できない構造にする
- 1セッションで扱う概念は3〜10個程度に絞る
- 各マイクロステップは「その2文だけ読めば次の質問に答えられる」自己完結性を持たせる

### Phase 3 の違い（Understanding モード）

**原則: 長い説明をしてから「理解できたか」確認するのではなく、最大2文の新情報＋その内容を問う質問を1ターンとして積み重ねる。読む負担を最小にし、理解度は内容質問の正誤で測る。**

1マイクロステップずつ以下のサイクルを回す：

1. テキスト出力（合計4文以内）：
   - 直前の回答へのフィードバック（1〜2文。正誤と、なぜそうなのか）
   - 次のマイクロステップの新情報（最大2文）
2. AskUserQuestionツールで、いま提示した2文を**適用すれば答えられる内容質問**を提示する
   - 「理解できましたか？」型のメタ質問は使わない
   - 誤答選択肢は、ありがちな誤解を反映したもっともらしいものにする
3. ユーザーの回答を評価：
   - **正答** → 次のマイクロステップへ（次ターン冒頭で短くフィードバック）
   - **誤答** → どこで誤解したかを特定し、そのステップをさらに小さい単位に分解して別の角度から再提示
   - **2回連続で誤答** → 前提となる概念（depends_on）に立ち返る

ユーザーの入力パターン：

| 入力 | 動作 |
|---|---|
| 選択肢クリック | 正誤を1〜2文でフィードバックし、次のマイクロステップへ |
| `分からない` | そのステップをさらに小さい単位に分解して再提示 |
| `back` / `戻る` | 前の概念に戻って復習 |
| `skip` / `飛ばす` | その概念を保留にして次へ |
| `summary` / `一覧` | 現在の理解状況（理解済み・途中・未到達）を表示 |

### ガイドライン

- 説明はIT文脈で行う（現実世界の例えは使わない）
- **1ターンの地の文は4文以内**（フィードバック最大2文＋新情報最大2文）。これを超えるならマイクロステップの分割が粗いサイン
- ユーザーが「分からない」と言ったら、決して同じ説明を繰り返さず、別の角度やより小さな単位に分解する
- 質問は常に内容を問うもの（適用・予測・区別）にし、「はい/いいえ」「理解できた？」は使わない
- 5概念に1回、それまでの理解の全体像を箇条書きの短いサマリーとして表示する

## ガードレール

**やらないこと：**
- 一気に複数質問しない — 必ず1問ずつ
- 候補なしで自由入力だけにしない — 必ず候補を提示
- 長文を読ませてから簡単な確認質問をしない — 質問の前のテキストは最小限（Understandingモードは4文以内）
- 推測を事実のように提示しない — 推測は候補の1つに留める
- 既存の文脈と矛盾する候補を出さない
- 変更が困難な決定を後回しにしない

**やること：**
- 前の回答を考慮して次の候補を絞り込む
- 「なぜこの候補を出したか」の理由を短く添える
- backで前の質問に戻れるようにする
- 自動決定したものは「何を・なぜ」を必ず開示する
